# Спул и очередь

Каждое письмо записывается в спул до отправки: цель, которая недоступна,
получит его при одном из следующих прогонов очереди. Здесь собраны
настройки `[spool]`, каталоги `tmp/`, `queue/`, `hold/`, `failed/` и
`locks/`, повторы, лимиты и `mailq`. При установке из пакета значения по
умолчанию менять не нужно.

## Настройки

```toml
[spool]                         # необязательно; значения - по умолчанию
dir = "/var/spool/mailcrier"    # "" выключает спул
drain_budget = "10s"            # прогон очереди после письма самого вызова
drain_max_messages = 20
run_budget = "60s"              # прогон очереди при -q
queue_ttl = "168h"              # затем queue/ -> failed/
hold_ttl = "168h"               # затем hold/ -> failed/
failed_ttl = "720h"             # затем удаляется
max_queue_messages = 1000
max_queue_bytes = 268435456
max_queue_messages_per_uid = 200
max_queue_bytes_per_uid = 67108864

[target.api]
type = "http"
url_file = "/etc/mailcrier.d/api.url"
preset = "generic-json"
```

## Письма в спуле и повторы

- Каждое письмо записывается в спул до доставки: исходное письмо как
  `queue/<id>.eml` и его состояние по каждой цели как `queue/<id>.json`;
  оба файла сначала пишутся в `tmp/`, сбрасываются на диск и переносятся
  в `queue/`. Состояние перезаписывается после каждой цели, а запись
  спула удаляется, когда письма больше не ждёт ни одна цель, или
  переносится в `failed/` с причиной `internal error`, если цель завершилась
  паникой (см. [Коды выхода](cli.ru.md#коды-выхода)). Цель с временной
  ошибкой остаётся в ожидании, и вызов завершается с кодом 0 и
  предупреждением `message queued` (или `message queued for target`, если
  письмо получила другая цель): письмо принято, как классический MTA
  принимает письмо в свою очередь.
- Прогон очереди повторяет попытку для ожидающей цели через минуту после
  первой ошибки, затем через вдвое больший интервал, чем предыдущий, не
  больше 24 часов, и никогда раньше задержки, которую служба запросила
  через `Retry-After`; если служба запросила задержку, до конца прогона
  эта цель пропускается и в других письмах. Письмо, пролежавшее в очереди
  дольше `queue_ttl` (задержанное - считая от его освобождения),
  переносится в `failed/` с ошибкой `message failed`, а через
  `failed_ttl` там удаляется. Удаляются файлы старше часа, оставленные
  убитым процессом: в `tmp/`, если их не держит живой процесс, и файлы
  состояния без письма в остальных каталогах. Файл письма без файла
  состояния, который `mailq` показывает как `unreadable`, - след
  прерванного удаления, когда письма уже не ждала ни одна цель: следующий
  прогон, дошедший до него, удаляет его и пишет в журнал
  `message without sidecar removed` с id и каталогом.
- Письмо в спуле, файл состояния которого не читается, остаётся на месте
  с предупреждением `spool entry unreadable, left alone` при каждом
  прогоне очереди, и прогон завершается с кодом 74. Повреждённый файл
  состояния потерял даты письма, поэтому их заменяет файл письма: он
  пишется вместе с записью спула и больше не перезаписывается; когда он
  старше `queue_ttl` (`hold_ttl` в `hold/`), запись переносится в
  `failed/`: причиной становится ошибка разбора, например
  `corrupt sidecar: unexpected end of JSON input`, а новый файл состояния
  без целей принадлежит владельцу файла. Владелец и возраст
  приблизительны: письмо, которое `-q` скопировал из `hold/` каталога по
  умолчанию, принадлежит пользователю того прогона и датируется
  копированием, а освобождённое из `hold/` считается со времени
  задержки, а не освобождения. Письмо сохраняется как было; если его
  заголовки называют получателей, `mailcrier -t < failed/<id>.eml`
  отправляет его снова. Повреждённый файл состояния в `failed/`
  удаляется вместе с письмом через `failed_ttl` после записи файла.
  Запись спула другой версии файла состояния остаётся нетронутой для
  версии программы, которая её записала, со своим предупреждением и
  кодом выхода 0.
- При повторе текст сохранённого письма строится по конфигурации и
  шаблонам на момент повтора, а цели остаются теми, что были выбраны при
  постановке в очередь. Переименование или удаление цели отбрасывает
  ожидающие её письма: для этой цели они завершаются ошибкой
  `target removed, message dropped for it`.

## Задержанные письма

- Письмо с отклонённой конфигурацией попадает в `hold/` (каталога по
  умолчанию, если файл не читается), и вызов завершается с кодом 78;
  первый прогон очереди с корректной конфигурацией маршрутизирует его как
  новое письмо, см. [Маршруты и подавление](routing.ru.md). Если
  корректный файл задаёт `dir`, отличный от каталога по умолчанию, `-q`
  переносит в эту очередь и то, что лежит в `hold/` каталога по
  умолчанию. Ожидание ограничено `hold_ttl`: пока файл отклонён, `-q`
  переносит просроченные письма в `failed/` и завершается с кодом 78 - в
  `dir` файла, если тот разбирается и отклонены только его цели, ведь
  вызов задержал письмо там, иначе в каталоге по умолчанию.
  Письмо, которое надо задержать из-за отклонённой конфигурации или
  отсутствия маршрута, но запись спула для которого не удалось создать
  или записать (`message lost, not held`), завершает вызов с кодом 73 или
  74 вместо 78 или 64, как временная ошибка без записи спула: письмо не
  сохраняется. Будет ли повторная попытка, решает вызывающая программа:
  cron, `mail()` PHP и большинство скриптов не различают коды выхода, а
  MTA, запускающий mailcrier как транспорт pipe, откладывает письмо
  только при 75 (Postfix) или при 75 и 73 (Exim) и возвращает его
  отправителю при остальных.

## Прогоны очереди

- Каждый вызов после доставки своего письма прогоняет очередь не дольше
  `drain_budget` и не больше чем по `drain_max_messages` письмам, только
  по письмам uid своей вызывающей программы, и не прогоняет вовсе, пока
  это делает другой вызов того же пользователя
  (`locks/drain-<uid>.lock`). `mailcrier -q` прогоняет её не дольше
  `run_budget`: root, пользователь `mailcrier` и процесс без бита setgid
  берут все письма, любой другой пользователь - только свои. Письмо
  блокируется, пока с ним работает процесс, и прогон пропускает
  заблокированные письма, поэтому параллельные прогоны никогда не
  доставляют письмо дважды.
- Пакеты запускают `mailcrier -q` от `mailcrier` каждые 5 минут: таймер
  systemd `mailcrier-queue.timer` (его служба останавливает прогон через
  3 минуты, чего хватает на `run_budget` в 60 секунд и идущую доставку;
  больший `run_budget` требует большего `TimeoutStartSec` в drop-in), а
  где systemd не запущен - `/etc/cron.d/mailcrier` или
  `/etc/crontabs/mailcrier` в Alpine, везде без почты от cron, так как
  `-q` пишет журнал только в syslog (`MAILTO=` для crond из BusyBox,
  который принимает `MAILTO=""` за адрес). Без запущенного демона cron
  или таймера, как в большинстве контейнеров, очередь прогоняют только
  сами вызовы; контейнер, который отправляет редко, запускает
  `mailcrier -q` из планировщика вроде supercronic, из контейнера-sidecar
  или из проверки работоспособности.

## Ограничения и гарантии

- Лимиты: все письма в `tmp/`, `queue/` и `hold/` вместе укладываются в
  `max_queue_messages` и `max_queue_bytes`, письма одного uid - в лимиты
  `_per_uid`; пользователи, кроме root и `mailcrier`, заполняют не больше
  80% общих лимитов, чтобы для почты root оставалось место в очереди.
  Параллельные вызовы вместе никогда не превышают лимит, но рядом с ним
  отказ могут получить все, хотя одно письмо поместилось бы. Письмо
  сверх лимита не ставится в очередь (`message not spooled` с
  `err="spool entry not created: quota exceeded: ..."`): оно всё равно
  доставляется, а временная ошибка тогда даёт код выхода 73.
- Письмо доставляется не менее одного раза: процесс, убитый после того,
  как служба приняла письмо, или таймаут после приёма повторяют эту
  доставку при следующем прогоне, и то же может случиться при отключении
  питания, поскольку состояние, записанное после доставки, не
  сбрасывается на диск до следующего шага. Если состояние не удаётся
  записать вовсе (`spool entry not updated`, полный диск), письмо в спуле
  остаётся таким, каким было до попытки: остаток этого вызова или
  прогона его пропускает, а следующий прогон, в другом процессе, находит
  его готовым к отправке и пробует снова без задержки повтора.
- Спул должен лежать на локальной файловой системе: блокировки (`flock`)
  не действуют между процессами по NFS. Каталог должен
  существовать; программа создаёт в нём недостающие `tmp`, `queue`,
  `hold`, `failed` и `locks`, что подходит для контейнера. При установке
  с битом setgid пакеты создают каталог и все пять подкаталогов как
  `root:mailcrier 2770`: созданные программой, они принадлежали бы
  пользователю, который отправил письмо первым. Записи спула создаются с
  режимом `0660`.

## Просмотр очереди

- `mailq` и `-bp` показывают письма из `queue/`, `hold/` и `failed/` с
  состоянием, числом попыток, следующей попыткой и последней ошибкой
  каждой цели - для root, пользователя `mailcrier` и процесса без бита
  setgid; остальные видят одну строку со счётчиками; несуществующий
  каталог спула показывается как `queue is empty`, выключенный спул
  (`dir = ""`) - как `spool off`. Нечитаемое письмо показывается как
  `<id> <area> unreadable err="..."` с причиной, которую пишет в журнал
  прогон очереди, например `corrupt sidecar: not a JSON object`.
  Последняя ошибка цели показывается под именем своего класса,
  `temp="status 503: Service Unavailable"`. `--status` печатает одну
  строку logfmt для мониторинга,
  `queued=1 held=0 failed=0 tmp=0 bytes=1432 oldest_age_seconds=75`, и
  завершается с кодом 74, если каталог не существует, а также, уже
  напечатав строку, если этот процесс не может писать в один из каталогов
  спула или файловая система только для чтения (`spool not writable`).
  Ни `mailq`, ни `--status` ничего не создают в спуле. `-q` на таком
  спуле завершается с кодом 74 без прогона
  (`spool not writable, queue not run`): иначе он доставил бы письма,
  которые не может отметить, и доставил бы их снова при следующем
  прогоне.
- Обе команды также учитывают, а `mailq` показывает с полем `dir="..."`,
  то, что лежит в `hold/` каталога по умолчанию и что `-q` переносит в
  ту очередь, когда файл задаёт другой `dir`; `bytes` и `tmp` остаются
  значениями этого `dir`, а каталог по умолчанию, который вызывающая
  программа не может прочитать, даёт предупреждение
  `default spool not listed` и остальной вывод. `-q` пользователя, кроме
  root и `mailcrier`, без права просматривать этот каталог не трогает
  его, с тем же предупреждением и кодом выхода 0: пользователь без бита
  setgid рядом со спулом пакетов не мог ничего там задержать; любая
  другая ошибка просмотра, как и ошибка у root или `mailcrier`, даёт
  код 74. При отклонённой конфигурации они показывают `dir` файла, если
  он разбирается и отклонены только цели, ведь вызов задерживает письмо
  там, иначе каталог по умолчанию, и пишут в журнал
  `spool listed under a rejected configuration` с каталогом. Пока
  отклонены только цели, `-q` не трогает каталог по умолчанию: то, что
  лежит в его `hold/`, не истекает и не переносится, а его `failed/` не
  чистится, пока цели не загрузятся снова.
- Когда `-q`, `mailq` или `--status` завершаются ошибкой или показывают
  спул при отклонённой конфигурации, в stderr помимо записи в журнале
  идёт по строке на каждую причину, интерактивен вызов или нет, например
  `mailcrier: spool not opened: stat /var/spool/mailcrier: no such file
  or directory` или `mailcrier: queue run incomplete, see the mail log`
  после прогона с ошибками на отдельных письмах. Вызывающая программа с
  повышенными правами через setgid получает строку без причины, а без
  syslog в stderr идут только записи. Под systemd журнал тогда содержит
  эту строку помимо записи; файл cron из пакетов её отбрасывает
  (`MAILTO=`).
